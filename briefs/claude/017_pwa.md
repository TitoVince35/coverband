# 017 - Progressive web app: review and proposal

> 🕒 Study posted on Tuesday 2026/10/20 15:06

Review of [017_pwa](../vince/017_pwa.md).

## Review

1. **The PWA is already on.** Production serves the manifest (name, icons, standalone display, dark colors), a service worker registered on every page, and automatic updates (vite-plugin-pwa). The app can be installed today from https://beta.coverband.fr. It was never seen on the local network because `serve:lan` is plain http, and service workers need HTTPS (or localhost). What is left to settle is what the PWA does.
2. **Updates can break an open app.** After a deploy, the new service worker takes over at once and deletes the old cached files, and the new container doesn't have the old build's files either. Each page has its own JS chunk: an app still open on the old version fails to load a page it hasn't visited yet ("Failed to fetch dynamically imported module"). An installed app also rarely reloads, so it can stay on an old version for days.
3. **Offline, the app opens but shows nothing.** The service worker caches the app's files only. No query cache is saved, and every API call fails without a connection. The session check on every page fails too, so the app would treat the user as logged out.
4. **`/api` must not be cached by the service worker.** The data is per user, behind a session cookie and the beta access code. A cache keyed by URL would survive logout and could serve one account's data to another on a shared phone. Offline data belongs to the app (TanStack Query persistence), which knows who is logged in.
5. **Installing is not obvious.** iPhones never offer it (Share › Add to Home Screen), and Android's prompt is easy to miss.
6. **No cache headers.** No response has a `Cache-Control` header today.
7. **TLS in every local mode has two traps.** HSTS, which our security headers send as soon as the app URL is https, would make the browser force HTTPS on every localhost port, other projects included, for a year. mkcert is not installed in CI or on a fresh clone.

## Decisions (Vince)

- **Offline data now** for bands, songs and lyrics, not after setlists.
- **The whole repertoire offline,** lyrics included, downloaded while online: at a gig, the song you need is the one you haven't opened.
- **Automatic updates,** no "new version" banner.
- **An install card on the home page** (the "Your bands" page after login).
- **TLS in every local mode** (`dev`, `dev:lan`, `serve`, `serve:lan`) with mkcert, the certificate reissued when the LAN IP changes. Without mkcert, plain http with a warning; the end-to-end tests stay on http.

## Proposal

### HTTPS in every local mode

- A certificate from mkcert for `localhost`, `127.0.0.1` and the current LAN IP, in a git-ignored folder, reissued at startup when an address is missing.
- The browser-facing server serves HTTPS: Vite in `dev` and `dev:lan` (it still proxies `/api` to the API over local http), the API (`Bun.serve` with `tls`) in `serve` and `serve:lan`. `BETTER_AUTH_URL` follows.
- `serve:lan` and `dev:lan` print a second QR code that downloads mkcert's root certificate (`rootCA.pem`), to install once on the phone. Android: Settings › Security › Install a certificate. iPhone: install the profile, then trust it in General › About › Certificate Trust Settings. **`rootCA-key.pem` never leaves the machine:** a phone trusting this authority accepts any certificate it signs. Remove it from the phone when done.
- No HSTS for `localhost` or an IP address.
- mkcert missing: plain http and a warning saying how to install it. The end-to-end tests and CI stay on http. Mailpit stays on http.

### Updates

- Reload the page when a page's code fails to load (Vite's `vite:preloadError`).
- Compare the app's version with `/api/health`'s at startup and when the app comes back to the foreground, and reload when they differ.
- Cache headers: the hashed files in `/assets/` cached for a year (`immutable`); `index.html`, `sw.js`, `registerSW.js` and the manifest with `no-cache`.

### Offline data

- TanStack Query persistence in IndexedDB for the user's bands, a band's page, the repertoire and the songs with their lyrics. Wiped on logout and when another account logs in; kept up to 30 days.
- **The whole repertoire:** a new endpoint returning all of a band's songs with their lyrics and links (members only). The app fetches it when a band is opened online and fills each song's cache from it. A few hundred KB for a big repertoire.
- The session offline: the last known user is kept instead of sending the user to the login page.
- Read-only offline: an "Offline: changes are disabled" banner, edit buttons turned off.
- Nothing from `/api` in the service worker.

### Install card

- On the home page, only when the app isn't running installed (`display-mode: standalone`), and dismissible (remembered on the device).
- Android and desktop Chrome: an "Install" button opening the browser's prompt (`beforeinstallprompt`). iPhone: the Share › Add to Home Screen steps. Hidden when neither applies.
- In both languages.

## Plan

An Epic with four issues:

1. HTTPS in every local mode.
2. Updates: reload on a failed page load, version check, cache headers.
3. Offline data: persistence, the whole-repertoire endpoint, the session offline, read-only mode.
4. Install card on the home page.

They are independent. Testing 3 and 4 on a phone is easier once 1 is done.
