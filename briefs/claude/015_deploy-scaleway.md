# 015 - Deploying to Scaleway

> 🕒 Study posted on Monday 2026/10/19 21:32

How CoverBand is deployed to Scaleway (#8): what was built, what was checked, and what can only be checked during the first real setup. Product choices and costs: `007_scaleway-products.md`.

## Decisions (Vince)

- **Infrastructure as code with OpenTofu**, rather than manual steps in the console.
- **Migrations run in the deploy job**, before the new version takes traffic, not when the container starts.
- **The container scales to zero**: about €0 a month, with a cold start of 1 to 3 s after a quiet period. `min_scale = 1` keeps one instance running for about €13 a month.
- **No Scaleway account or domain yet**: everything uses placeholders until they exist.

## Checked so far

Nothing has run against Scaleway yet.

- **Docker image:** it builds and runs against the local Postgres, Mailpit and Garage. The health check, the web app and app routes all answer.
- **OpenTofu:** `tofu validate` passes against the current Scaleway provider (2.87), so the resource and field names are current.
- **`bun run check`:** passes.

## What was built

- **`Dockerfile`, `.dockerignore`:** two stages. The final image (404 MB) has only the API's runtime dependencies and the built web app.
- **`infra/` (OpenTofu):**
  - Resources: registry, database (scales to zero, at most 1 vCPU), private bucket, email on your domain, the container (scales to zero, 0.56 vCPU / 1 GB, HTTPS only), `app.<domain>` with its DNS record, and a budget alert at 50/90/100% (default €20).
  - Secrets are generated by OpenTofu and passed to the container as secret variables, including the auth secret and the admin password (`tofu output -raw admin_password`).
  - The state is encrypted with a passphrase, since it holds every secret.
- **Two access keys:**
  - The container's key can only read and write data (no table changes), handle files and send email.
  - The deploy key pushes the image, updates the container, and runs migrations.
- **`.github/workflows/deploy.yml`:** runs after CI passes on `main`, or by hand. It builds and pushes the image, runs migrations while the old release still serves, switches the container to the new image, waits until it's ready, then calls `/api/health`.
- **`infra/github-secrets.sh`:** copies the deploy settings from the OpenTofu outputs into a GitHub `production` environment.
- **`ci.yml`:** a new job builds the image and validates the `infra/` code on every PR.
- **`infra/README.md`:** the first setup in order. It pushes the first image and runs migrations before the container is created; otherwise the container would crash at startup with no tables. It also covers day-to-day changes. Both `CLAUDE.md` files now say how deployment works.

## Left for the first real setup

- **Client IP for the login rate limit:** this part of the issue can only be checked once deployed. Step 11 of `infra/README.md` shows how; if it fails, the fix is setting `trusted_proxies` in `terraform.tfvars`.
- **Table access for the container:** Scaleway's docs suggest the data-only access can use tables created by the deploy key, but don't say so outright. If it can't, the container's database permission in `infra/iam.tf` needs to become `ServerlessSQLDatabaseReadWrite`.
- **Domain:** buy it at Scaleway first. The setup assumes Scaleway hosts its DNS, which lets Scaleway write the email records (SPF, DKIM) itself.
