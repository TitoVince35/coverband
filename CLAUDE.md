# CoverBand

An installable web app (PWA) for music bands: repertoire, setlists, gigs, members.
Multi-tenant: each band's data is private; a musician can belong to several bands.

Product briefs and technical decisions live in `briefs/` (see below). Read them before making structural choices.

## Stack

- **Bun** workspaces monorepo, TypeScript strict everywhere
- `apps/api`: Hono on Bun, REST API under `/api` plus the built web app (single container)
- `apps/web`: React + Vite + TanStack Router/Query, Tailwind + shadcn/ui, vite-plugin-pwa
- `packages/shared`: code shared by both apps (Zod schemas, types, helpers)
- PostgreSQL + **Drizzle** ORM, **Better Auth** (organization plugin: band = organization)
- Hosting: Scaleway (Paris), Serverless Containers + Serverless SQL Database + Object Storage
- Tooling: Biome (lint + format), `tsc` for typechecking, `bun test`, Playwright for end-to-end tests

## Commands

```sh
bun install          # install all workspaces
bun run check        # lint + typecheck + tests (run before every commit)
bun run dev          # API (http://localhost:3000) + web app (http://localhost:5173, proxies /api)
bun run dev:api      # API only, watch mode
bun run dev:web      # web app only (Vite)
bun run build        # build the web app into apps/web/dist
bun run serve        # production-like: the API serves apps/web/dist on :3000 (open http://localhost:3000)
bun run format       # apply Biome formatting and safe fixes
bun test             # tests only (DB integration tests are skipped when DATABASE_URL is unset)

cp .env.example .env # first time only
bun run db:up        # start local Postgres (Docker, port 5432)
bun run db:generate  # generate a SQL migration from apps/api/src/db/schema.ts
bun run db:migrate   # apply pending migrations
bun run db:studio    # browse the database
bun run db:down      # stop Postgres (add -v to docker compose down to wipe data)
```

## Conventions

- Code, comments, commits, issues and PRs in English.
- Tests sit next to the code: `foo.ts` → `foo.test.ts`, using `bun:test`.
- Workspace packages are imported by name (`@coverband/shared`), never by relative path across packages.
- **API:** REST under `/api` (resource URLs, HTTP verbs, status codes, JSON). One Hono sub-app per resource in `apps/api/src/routes/`, mounted in `src/app.ts` with chained calls so `AppType` keeps every route. The web app calls it through the typed client from `@coverband/api/client` (Hono calls this "RPC"; see `briefs/claude/003_rest-vs-rpc.md`). Errors are JSON `{ "error": { "code", "message" } }`, sent with `apiError()` (`apps/api/src/errors.ts`): `code` is a stable code from `ERROR_CODES` in `@coverband/shared` that the web app translates; `message` is an English fallback for developers. No OpenAPI for now.
- **Web app:** file-based routes in `apps/web/src/routes/` (TanStack Router; `routeTree.gen.ts` is generated by the Vite plugin and committed, never edit it). Server data goes through TanStack Query and the typed `api` client from `@/lib/api`. Import app code with the `@/` alias. Mobile-first: design for a phone, then widen.
- **UI components:** shadcn/ui (Radix base) in `apps/web/src/components/ui/`, added with `bunx --bun shadcn@latest add <name>` from `apps/web`. Icons from `lucide-react`. `cn()` comes from shadcn's `cn` package. Theme from shadcn preset `b6p43rVk5Q` (style `radix-maia`, mauve neutrals, emerald primary, Noto Sans body, Montserrat headings via `font-heading`); theme tokens live in `apps/web/src/index.css`. Brand colour `#007a55` (emerald-700) is used for the logo and the light-mode `theme-color`.
- **Colour theme:** dark by default, with a Light / Dark / System switch in the header, saved in `localStorage` (`coverband-theme`). Logic in `apps/web/src/lib/theme.ts`, duplicated in an inline script in `apps/web/index.html` that applies it before first paint: keep both in sync. Always style for both themes (`dark:` variants or theme tokens like `bg-background`).
- **PWA:** configured in `apps/web/vite.config.ts` (vite-plugin-pwa, auto-update). Icons in `apps/web/public/` are generated from `public/logo.svg` with `bunx pwa-assets-generator --preset minimal-2023 public/logo.svg`.
- **i18n (from day one):** English (default and fallback) and French. Never hardcode user-visible text: add the key to both `apps/web/src/i18n/locales/en.json` and `fr.json` and use `t("section.key")` from `useTranslation()`. Keys are typed from `en.json` (a typo fails the typecheck) and a test checks both files have the same keys. Language = saved choice (`localStorage` `coverband-language`), else the browser's languages, else English. Format dates and numbers with `Intl` and `i18n.language`; durations stay `m:ss` via `formatDuration`. Display API errors with `errorMessage(t, error)` from `@/lib/errors` (use `ensureOk(res)` on API responses). A new API error code needs a translation in both files (tested). Language names in the switch stay in their own language.
- **Authentication:** Better Auth in `apps/api/src/auth.ts`, mounted at `/api/auth/*`; tables in `src/db/auth-schema.ts` (generated with `npx auth generate`, then adapted: regenerate and compare when adding a Better Auth plugin). Email + password, sessions in Postgres, **no public sign-up** (accounts only come from invitations), password policy from `@coverband/shared` (`PASSWORD_MIN_LENGTH`). Global role on the user: `admin` or `user` (admin plugin); band roles (leader, musician) live on the band membership, never on the user. The default admin is created at startup from `ADMIN_EMAIL` / `ADMIN_PASSWORD` only if missing (`src/bootstrap.ts`). API routes read `c.var.user` and guard with `requireUser` / `requireAdmin` (`src/middleware/session.ts`). Web: `authClient` and `sessionQuery` from `@/lib/auth`; pages needing a login go under `routes/_app/` (pathless layout that redirects to `/login`), public pages (login, invitations) outside it.
- **Multi-tenancy:** every band-scoped table has a `band_id`; every band-scoped request checks that the user is a member of that band. The band is in the URL (`/b/:bandSlug/...`).
- **Stateless server** (it runs on serverless containers): no in-memory sessions or caches that matter, no local file storage, no in-process cron. Sessions in Postgres, files in object storage.
- Postgres goes through Scaleway's connection pooler: use the `postgres` driver with `prepare: false` (see `apps/api/src/db/client.ts`).
- Drizzle uses `casing: "snake_case"`: write camelCase in TypeScript, get snake_case columns. Commit generated migrations in `apps/api/drizzle/`; never edit an applied one.
- Environment variables are validated with Zod in `apps/api/src/env.ts`; add new ones there and in `.env.example`.

## Task workflow (GitHub Projects)

Board: https://github.com/users/TitoVince35/projects/1. Columns: Backlog → Todo → In progress → In review → Done. Sprints are 2-week iterations (`Sprint` field).

For each task (issue `#NN`):
1. Move it to **In progress** and create a branch `NN-short-title` from `main`.
2. Commit with `bun run check` passing.
   CI (`.github/workflows/ci.yml`) runs lint, typecheck, migrations, tests (with a Postgres service, so DB tests run) and the web build on every PR and on `main`. Keep it green: a PR is ready for review only when CI passes.
3. Push and open a PR whose body contains `Closes #NN`. The board automation moves it to **In review**.
4. Vince reviews and merges. Automation moves the task to **Done** and closes the issue.

New issues created in the repo are added to the Backlog automatically.

Moving a task with `gh` (the only manual move is to In progress):

```sh
# find the item id of issue NN
gh api graphql -f query='{ node(id:"PVT_kwHOADAgOs4BnNj-"){ ... on ProjectV2 { items(first:100){ nodes{ id content{ ... on Issue{ number } } } } } } }' \
  --jq '.data.node.items.nodes[] | select(.content.number==NN) | .id'
# set its status
gh project item-edit --project-id PVT_kwHOADAgOs4BnNj- --id <item-id> \
  --field-id PVTSSF_lAHOADAgOs4BnNj-zhlzNcM --single-select-option-id <option-id>
```

Status option ids: Backlog `68d1018a`, Todo `4690f79a`, In progress `0c86fcb5`, In review `cc8e2739`, Done `19ed2183`.
Sprint field `PVTIF_lAHOADAgOs4BnNj-zhlzNx8`: Sprint 1 `3c4d0bab`, Sprint 2 `36e02d73`, Sprint 3 `964b06f5`.

Newly added board items can take minutes to show up in the board API and views (GitHub indexing lag); `gh issue view NN --json projectItems` is reliable immediately.
