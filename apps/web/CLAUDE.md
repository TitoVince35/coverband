# Web app (`apps/web`)

React + Vite + TanStack Router/Query. Cross-cutting rules are in the root `CLAUDE.md`. **Mobile-first:** design for a phone, then widen.

## Routes and data

- File-based routes in `src/routes/` (TanStack Router). `routeTree.gen.ts` is generated by the Vite plugin and committed; never edit it.
- Pages needing a login go under `routes/_app/` (pathless layout that redirects to `/login`); public pages (login, invitations) outside it.
- Beta access code (#148): the root route sends every page but the open ones (`isOpenPage`, `src/lib/open-pages.ts`: `/access`, `/invite/…`, `/reset-password`) to `/access` while `accessQuery` (`src/lib/access.ts`) says the code is needed and not given. The login page and the code screen show the version (`AppVersion`, #147).
- Band pages go under `routes/_app/b.$bandSlug/`, inside the band layout (`b.$bandSlug.tsx`: the band's name opening the band menu, `BandSwitcher`: its settings, other bands; then its sections, `BandNav`, #223: Home, Repertoire, Lineup, and Setlists and Gigs shown disabled until they exist, each with an icon and a label; tabs on a large screen, a bottom bar on a phone, put on the body by a portal, clear of the home indicator, the band layout leaving room for it, hidden while the keyboard is up, `useKeyboardUp` in `src/lib/keyboard.ts`, read from the visual viewport's height, never the focus). **A suspended band** (#248: an admin disabled it): the band list says "Suspended", the band layout shows only `BandSuspended` (the API's `band_suspended`; `bandQuery` doesn't retry it, nor `not_found`), and nothing of it is kept offline. **Band settings** (#221, `settings.tsx`): the genre (`BandDetailsForm`) and the logo, for the band leader only: the menu shows them disabled to musicians, and the page sends a musician back to the band's home.
- Server data goes through TanStack Query and the typed `api` client from `@/lib/api`. Use `ensureOk(res)` on API responses and display errors with `errorMessage(t, error)` from `@/lib/errors`.
- **Cache:** queries are fresh for 5 minutes (`STALE_TIME`, `createQueryClient()` in `src/lib/query-client.ts`), so focus and reconnect don't refetch: the serverless database is billed per minute awake. A query whose data changes elsewhere and must be exact sets a shorter `staleTime` (the invitation page uses 0). **Every mutation invalidates the queries it changes**, so the user's own changes show at once. Logging out uses `clearUserData()` and logging in `removeUserQueries()`, so another account never sees the previous one's cached data. Queries are never garbage-collected (`gcTime: Infinity`: the offline copy saves what's in memory). Route guards read the session and the access check with `guardData()`: the server's answer online (reused while fresh), the saved copy offline or when the server can't be reached. Guards run on every navigation, so **they never wait on data the server already gave** (#211): stale data fetched since the app started is answered at once and checked again in the background, and `watchGuardData` (`main.tsx`) runs the guards again (`router.invalidate()`) when that answer changes (logged out elsewhere, a new access code); only at startup (saved data) do they wait for the server.
- **Offline (#165):** the cache is saved in IndexedDB (`src/lib/offline-cache.ts`, a delayed single write, flushed when the page is hidden) and restored before the first render; another build drops it, and what's restored counts as stale (fetched again online). Only what reading a band needs is saved (`isKeptOffline`: session, access check, bands, a band's page, journal, lineup, repertoire and songs; never invitations or lyrics searches). The session is kept without its token, IP or browser (`appSession`, `src/lib/session.ts`). The logged-in layout (`_app.tsx`) loads every band of the user for offline use while online, whichever page opens after login (`useKeepBandsOffline`, `src/lib/offline-bands.ts`, again each time the bands are fetched again): its queries, plus the whole repertoire with lyrics and links (`songDetailsQuery`, `GET …/songs/details`) filling every song's query. That load is a query itself, so it is skipped while fresh and goes with the user's data on logout or login (#174). Band logos are files, kept apart (#178, `src/lib/offline-logos.ts`): `keepBandOffline` saves each band's full logo in the same database's `logos` store (one per band slug, downloaded only when its versioned URL changes, deleted once the band has none, dropped after 30 days, emptied by `removeUserQueries`); `BandLogo` shows the server's image online, the saved copy offline or when the server's image doesn't load, else the initials. Songs' photos and PDFs too (#240, `src/lib/offline-documents.ts`): saved in the same database's `documents` store when the repertoire's details are fetched (`keepDocumentsOffline`, each downloaded once, removed once gone), the newest first within `OFFLINE_DOCUMENTS_MAX_BYTES` for every band together (`documentsToKeep`, tested), emptied by `removeUserQueries`; offline, the Documents block opens them from there (`DocumentLink`), and Guitar Pro and MuseScore files say they need the network. Nothing from `/api` goes through the service worker. Offline, the app is read-only: `OfflineBanner` in the root layout, and **every button that starts a change is disabled with `useOnline()`** (`src/lib/online.ts`; a new one too); mutations use `networkMode: "always"`, so one started anyway fails at once with the network error instead of being sent later. TanStack Query's online state starts from `navigator.onLine` (`main.tsx`).
- Auth: `authClient` and `sessionQuery` from `@/lib/auth`. Wrap Better Auth client calls in `ensureAuthOk()`, which throws an `AuthRequestError` (status + Better Auth code such as `INVALID_TOKEN`).
- A new password is always typed twice with `NewPasswordFields` / `readNewPassword` (`src/components/account/`): onboarding, reset and change forms.
- Import app code with the `@/` alias.

## UI

- **Loading (#190): never a blank screen.** While a query is pending, show a skeleton shaped like what's coming (`ListSkeleton`, `BandSkeleton`, `SongSkeleton` in `src/components/loading.tsx`, on shadcn's `Skeleton`), never `null` or a bare "Loading…"; it appears after `LOADING_DELAY_MS` (150 ms), so cached data never flashes one. A loading area is a `status` named "Loading…" for screen readers. **Every mutation shows it's running (#208):** its button gets `pending` (`Button`, `src/components/ui/button.tsx`: a spinner instead of its icon, disabled meanwhile), a confirmation that closes at once puts it on the button that opened it, and a one-tap picker shows a small spinner (`StatusPicker`, `EnergyPicker`); a search shows a skeleton of its results. Route guards waiting show `PageSpinner` (the router's `defaultPendingComponent`, only for a layout not shown yet); any navigation that waits shows `NavigationProgress`, a thin bar under the header (#211), so the page shown never just freezes, and `index.html` has a spinner until the app's code loads. To see them, the development tools in the header (development only) have a **slow network** switch (#197, `src/lib/slow-network.ts`): every API request waits 2 s while it's on, remembered on the device (`localStorage` `coverband-slow-network`).
- shadcn/ui (Radix base) in `src/components/ui/`, added with `bunx --bun shadcn@latest add <name>` from `apps/web`. Icons from `lucide-react`. `cn()` comes from shadcn's `cn` package.

- **Colour theme:** dark by default, with a Light / Dark / System switch in the header, saved in `localStorage` (`coverband-theme`). Logic in `src/lib/theme.ts`, duplicated in an inline script in `index.html` that applies it before first paint: **keep both in sync**. Always style for both themes (`dark:` variants or theme tokens like `bg-background`).
- Show a person with `UserAvatar` (`src/components/user-avatar.tsx`): their photo from an `avatarUrl` (the API gives it; for the session user, `sessionAvatarUrl(user)`), else a `boring-avatars` face drawn from their ID. A list of instruments shows with `InstrumentTags`; members edit their own in a band from their lineup row (`EditInstrumentsDialog`, `src/components/instruments/`).

## i18n

- Add every key to both `src/i18n/locales/en.json` and `fr.json` and use `t("section.key")` from `useTranslation()`. Keys are typed from `en.json` (a typo fails the typecheck) and a test checks both files have the same keys.

## PWA

`vite.config.ts` imports `APP_NAME` from `@coverband/shared` (manifest, `%APP_NAME%` in `index.html`): the `dev`, `build` and `preview` scripts use `--configLoader runner` so Vite can load the shared package's TypeScript.

Configured in `vite.config.ts` (vite-plugin-pwa, auto-update). The service worker only runs in the built app (`bun run serve`, `serve:lan`), over HTTPS or on localhost: see Local HTTPS in the root `CLAUDE.md` to test on a phone. Icons in `public/` are generated from `public/logo.svg` with `bunx pwa-assets-generator --preset minimal-2023 public/logo.svg`. The installed app's icons (`maskable-icon-512x512.png` for Android, `apple-touch-icon-180x180.png` for iPhone) come from `public/logo-maskable.svg` instead: plain green to the edges, the artwork within the safe zone (a centred circle of 40% of the width), since the phone cuts its own shape (round on most Android phones). The preset would put them on white with a margin, so generate them again from `logo-maskable.svg` afterwards (a config with `maskable: { sizes: [512], padding: 0 }`, `apple: { sizes: [180], padding: 0 }`, both with `resizeOptions: { background: "#007a55" }`, empty `transparent` sizes and favicons). The browser tab uses a simpler mark that stays sharp at 16 px: a guitar pick with a C, drawn on a 32 px grid (`public/favicon.svg`). The preset overwrites `favicon.ico`, so generate it again from `favicon.svg` afterwards (a config with `transparent: { sizes: [], favicons: [[48, "favicon.ico"]], padding: 0 }`, empty `maskable` and `apple` sizes).

- **Updates are silent** (#164, `src/lib/app-updates.ts`, production builds only). After a deploy, the new service worker deletes the old build's files and the new container doesn't have them: an app still running the old build would fail to open a page it hasn't loaded yet. So the app reloads when a page's code fails to load (Vite's `vite:preloadError`, once per 30 s), and compares its build with `/api/health`'s at startup and when it comes back to the foreground (at most once a minute): another build lets the new service worker take over, then reloads, once per server build.
- The API serves the hashed files of `/assets/` with a one-year `immutable` cache, everything else of the build with `no-cache`, and a missing `/assets/` file as a 404 (never the app shell).
- **Install card** (#166, `InstallCard` on the home page, `src/lib/install.ts`): shown while the app isn't running installed (`display-mode: standalone`, or iOS's `navigator.standalone`) and until dismissed (`localStorage` `coverband-install-dismissed`). Chrome and Android: an Install button opening the browser's prompt (`beforeinstallprompt`, caught from the start by `listenForInstall()` in `main.tsx`, since it fires once and early); iPhone and iPad: the Share › Add to Home Screen steps; elsewhere, nothing. The rules are `installMode` and `isIos` (tested); the e2e test uses an iPhone user agent, as Chrome never prompts under automation.
