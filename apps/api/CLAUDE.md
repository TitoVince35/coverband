# API (`apps/api`)

Hono on Bun. Cross-cutting rules are in the root `CLAUDE.md`.

## Layout

- `src/modules/<feature>/`: one folder per feature (admin: the admin app's routes, `GET /api/admin/stats` for its homepage numbers, each counted by its own module's service, `GET /api/admin/bands` (a page: `adminBandPage`, searched, sorted, with member counts and leaders) and `/bands/:id` (`adminBandDetails`: lineup, counts, storage, journal), `POST /bands/:id/disable` and `/enable` (`setBandDisabled`, #248), `DELETE /bands/:id` with the band's name typed again (`deleteBand`: only a disabled band, 409 `band_not_disabled`, 400 `band_name_mismatch`; the rows by cascade in one transaction, then its documents' and logo's files); `GET /users` (a page: `adminUserPage`, searched by email or names, `admins` and `bandless` filters, with bands and instruments) and `/users/:id` (`adminUserDetails`: last session, pending invitations, `impersonateUrl`), `POST /users/:id/ban` and `/unban` (`setUserBanned`: Better Auth's admin plugin's `banned` flag refuses logins, blocking ends the sessions; `user.banned`, `user.unbanned`), `POST /users/:id/password-reset` (Better Auth's reset email, in the language of their latest invitation), `DELETE /users/:id` (`deleteUser`: 409 `only_band_leader` with the bands in its details; `user.deleted`, then the avatar's file); never on an admin nor oneself (403), #249; bands, members, instruments, invitations, onboarding, profile, journal, songs, autofill, contact, notifications). `routes.ts` (Hono sub-app), `service.ts` (the feature's rules and queries, its transactions and activity), `schema.ts` (its Drizzle tables, when it has some), tests next to them.
- `src/core/`: what every feature uses, knowing none of them: `errors.ts`, `log.ts`, `db/` (client, migrations runner, `schema.ts` re-exporting every table for Drizzle), `http/` (request logs, session guards, validation, rate limiter, security, health), `activity/` (recording and purging events).
- `src/adapters/`: the outside world behind small interfaces: `auth.ts` (Better Auth, with its tables in `auth-schema.ts`), `storage.ts`, `mail/`, `lyrics.ts`.
- `src/app.ts` is the composition root: it mounts every module's sub-app (a band's features under `/bands/:bandSlug/...`). `src/main.ts` builds the real dependencies and starts the server.
- Rules, checked by `src/architecture.test.ts` (so by `bun run check`): routes call their module's service and never query the database; only routes and guards import Hono; a module uses another one only through its `service.ts` (or the bands `guard.ts`), and only its own tables plus the auth adapter's (`users`...) and core's (`activity`); `core/` uses no feature; no import cycle between modules. When a module needs another one's data, add a function to that module's service rather than an exception to the check.
- **Moving or renaming files:** see the `task-workflow` skill (move-only commits).

## Routes

- REST under `/api` (resource URLs, HTTP verbs, status codes, JSON). No OpenAPI for now.
- One Hono sub-app per resource, in its module's `routes.ts`, built by a function taking `AppDeps` (`src/deps.ts`: auth, db, log, mailer, storage, lyrics, appUrl) and mounted in `src/app.ts` with **chained calls** so `AppType` keeps every route. The web app calls it through the typed client from `@coverband/api/client` (Hono calls this "RPC"; see `briefs/claude/003_rest-vs-rpc.md`).
- Routes don't query the database (no `drizzle-orm` or `db/schema` import): they validate, call their module's service and shape the response.
- Validate input with `zValidator(..., validationHook)` (`src/core/http/validation.ts`: invalid input becomes a 400 `bad_request`). Request bodies are Zod schemas in `@coverband/shared/schemas` (shared with the web app; a separate entry so Zod stays out of the web bundle until it uses one); route params and queries stay in the routes.
- Send errors with `apiError()` (`src/core/errors.ts`). It keeps the status as a literal type, so `ensureOk(res)` in the web app narrows typed-client responses to their success body.
- **Domain refusals** (a duplicate, an expired invitation...) are thrown as an `AppError(code, message, details?)`, or a subclass named after the case (`DuplicateSongError`). The domain never knows HTTP statuses: `ERROR_STATUS` (`src/core/errors.ts`) gives each code its status, and the app's `onError` sends the JSON error. Routes don't catch them. A new code goes in `ERROR_CODES`, `ERROR_STATUS` (the typecheck asks) and both web locales.
- Postgres refusals are recognised with `isForeignKeyViolation` / `isUniqueViolation(error, constraint)` (`src/core/db/pg-errors.ts`).
- Guards: `requireUser` / `requireAdmin` (`src/core/http/session.ts`). They are typed so the routes after them read a non-null `c.var.user`: never fall back to `?? ""`. A band's features are sub-apps mounted under `/api/bands/:bandSlug/<feature>` in `src/app.ts`, each starting with `.use(requireMember(db))` (`src/modules/bands/guard.ts`: sets `c.var.band` and `c.var.membership`, 404 for non-members), so the guard runs once per request. Band leader actions add `requireLeader` (403).
- Tests build dependencies with `createTestDeps()` (`src/test-deps.ts`, memory mailer and storage).

## Security

- Security headers on every response, API and web app (`src/core/http/security.ts`, Hono's `secureHeaders`): CSP, `Referrer-Policy: no-referrer` (tokens are in invitation and reset URLs), `X-Frame-Options: DENY`, a `Permissions-Policy` turning off camera, microphone and geolocation; HSTS only when `BETTER_AUTH_URL` is HTTPS on a real domain (`wantsHsts`: never `localhost` or an IP, whose local HTTPS would otherwise force HTTPS on every localhost port).
- The CSP only allows our own origin. The inline theme script of `apps/web/index.html` is allowed by its hash (`THEME_SCRIPT_HASH`): when the script changes, the test fails and shows the new hash. Inline styles stay allowed (React style props, toasts). Images also allow `data:` and `blob:` (previews before upload, offline band logos). Anything loaded from another origin (fonts, images, scripts) needs a CSP change.
- Guards on `/api/*`, Better Auth included (`requestGuards`): request bodies up to 100 KB (413 otherwise), but the upload routes given their own limit in `src/app.ts` (`largerBodies`: the band logo, `LOGO_UPLOAD_MAX_SIZE`), and `hono/csrf`, which refuses form-style requests (form, multipart, `text/plain`) from other origins than the app URL and `TRUSTED_ORIGINS`.
- Rate limits. Better Auth limits its own endpoints per client IP (login and password change: 3 per 10 s; reset requests: 3 per minute; others: 100 per 10 s), with counters in Postgres. Our routes that send emails use `rateLimitUser(db, rule)` (`src/core/http/rate-limit.ts`, fixed window per user, stored in the same `rate_limits` table with `coverband:` keys): invitation send and resend, 20 per hour (`INVITATION_EMAILS`, `src/modules/invitations/routes.ts`); lyrics searches, which call LRCLIB, 30 per hour (`LYRICS_SEARCHES`, `src/modules/songs/routes.ts`). `rateLimitBy(db, rule, subject)` limits by another subject: autofill searches, 15 per band and day (`AUTOFILL_SEARCHES`). Over the limit: 429 `too_many_requests` with `Retry-After`.
- Client IP: Better Auth reads it from one header, `CLIENT_IP_HEADER`: `x-forwarded-for` by default (the e2e tests give each login its own), `x-real-ip` in production (`infra/container.tf`). Scaleway's proxy overwrites `X-Real-IP`, while a client can send its own `X-Forwarded-For` and dodge the limits.
- **Beta access code** (#148, `src/core/http/access.ts`): with `BETA_ACCESS_CODE` set, `/api/*` answers 403 `access_required` without the `coverband_access` cookie (an HMAC of the code with the auth secret, so changing the code shuts every device out), before Better Auth and any session lookup. Open: `/api/health`, `/api/access` (`GET`: required/granted; `POST { code }`: sets the cookie, `ACCESS_CODES` limit per client IP, 403 `access_code_invalid`), `/api/auth/get-session`, and the email-link routes (`/api/invitations/*`, `/api/auth/reset-password*`): following a valid invitation or reset link sets the cookie. Empty: no gate (development, tests).
- **Cron jobs** (#45, `src/core/http/internal.ts`): the server can't schedule anything itself, so Scaleway cron triggers (`infra/cron.tf`) call `POST /api/internal/*` with `Authorization: Bearer <CRON_SECRET>` (401 otherwise) and a JSON body (without a content type, `hono/csrf` takes the call for a form post). Mounted only when `CRON_SECRET` is set; outside the typed API, and open past the beta access gate. A new job: a route there plus a trigger in `infra/cron.tf`.
- Search engines are kept out (#149): `X-Robots-Tag: noindex, nofollow` on every response (`noIndex`, `src/core/http/security.ts`) and `apps/web/public/robots.txt` disallowing everything.
- **The admin app's host** (#246, `src/core/http/admin-host.ts`): with `ADMIN_URL` set, requests for its hostname (any port) get the built admin app (`ADMIN_DIST_DIR`) instead of the web app, and only `/api/health`, `/api/auth/*` and `/api/admin/*` (`adminHostApi`: 404 otherwise), without the beta access code (an account is as good a proof, and only logging in and the admin routes are there). `ADMIN_URL` is also a trusted origin for Better Auth and `hono/csrf`. Session cookies stay on the host that set them.
- Other hostnames of the container (`REDIRECT_HOSTS`: the bare domain in production, #156) get a 301 to the app URL, path and query kept (`redirectHosts`, `src/core/http/redirect.ts`).
- The built web app's cache headers (#164, `staticCacheHeaders`, `src/core/http/static-cache.ts`): `/assets/*` (hashed names) cached for a year, `immutable`; the rest (`index.html`, `sw.js`, the manifest...) `no-cache`. A missing `/assets/` file is a 404, never the app shell.
- **No CORS, on purpose.** The API serves the web app on the same origin in production, and Vite proxies `/api` in development. CORS would only loosen the browser's cross-origin rules: never add it.

## Logs

- Technical logs only (#42): functional events go to the activity table. One line per entry on stdout, which Scaleway sends to Cockpit: JSON (`time`, `level`, `msg` + fields) in production, a readable line with `LOG_FORMAT=pretty`. `LOG_LEVEL`: `debug`, `info` (default), `warn`, `error`. Our own logger, no dependency (`src/core/log.ts`).
- In a request, log through `c.var.log`: it carries `requestId` (also sent as `X-Request-Id`, always ours), then `userId` (set by `loadSession`) and `bandId` (set by `requireMember`). A service that logs gets it from its route (`{ ...deps, log: c.var.log }`); `deps.log` is for outside requests (startup).
- `requestLog` (`src/core/http/request-log.ts`, first middleware) logs each request once answered, **by route pattern, never the raw path** (tokens are in invitation URLs): `error` for unhandled errors (the 500s of `onError`, with the stack), `warn` for other 5xx and requests slower than `SLOW_REQUEST_MS` (1 s), `debug` for the rest. 4xx are normal answers: not logged, except our 429s (`warn` with the rule, `rateLimitUser`).
- **An external service that fails is logged as an `error` (#208)**, with its cause in `err`, and the member is told it's an error, never shown its message: an `AppError` given a `cause` (`LyricsUnavailableError`: LRCLIB) is logged by the app's `onError`; a search that still answers (autofill) logs it in its service and lists the failed services in its answer. A new external call follows the same rule.
- Also logged: startup and the default admin (`info`, `src/main.ts`), migrations (`info`), a password reset email that fails (`error`, the answer stays the same), an old avatar left in the bucket (`warn`). A failed invitation email is a 500, logged by `requestLog`. Better Auth logs through ours (`betterAuthLogger`, emails masked in its messages).
- **Never log emails, names, tokens or passwords:** IDs only. Errors go in an `err` field (serialized with their stack).
- Tests: `createTestDeps()` gives a silent logger; `createMemoryLogger()` keeps the entries to check them. A test app built without `createApp` that uses `loadSession` needs `requestLog(silentLogger)` first.

## Database

- Postgres goes through Scaleway's connection pooler: use the `postgres` driver with `prepare: false` (`src/core/db/client.ts`).
- Drizzle uses `casing: "snake_case"`: write camelCase in TypeScript, get snake_case columns.
- Commit generated migrations in `drizzle/`; never edit an applied one.
- Environment variables are validated with Zod in `src/env.ts`; add new ones there and in `.env.example`.

## Activity

- **Every write records its event** in the `activity` table (`src/core/activity/schema.ts`): base for stats and the future activity feed. A new feature adds its codes to `ACTIVITY_ACTIONS` (and targets to `ACTIVITY_TARGETS`) in `@coverband/shared`; codes never change once used.
- Call `recordActivity(tx, ...)` (`src/core/activity/record.ts`) with the transaction of the change itself: no event without its change, no change without its event. Refused or failed attempts record nothing.
- `band_id` is null for events outside a band (band leader invitations, new accounts); band activity is deleted with its band. `actor_id` becomes null when the account is deleted.
- `data` holds small, non-personal details: IDs, roles, codes, a genre. **Never emails or names.**
- Invitations record `invitation.sent` only once the email has gone out, since a failed send deletes the invitation.
- **Band journal:** `GET /api/bands/:bandSlug/activity` (`bandJournal`, `src/modules/journal/service.ts`, members only): the band's latest `JOURNAL_SIZE` (10) events, newest first, with the actor's current display name (null once deleted) and only the details a sentence needs (`JournalDetails`: a song's title, its new status, the new genre); a leader's `member.joined` is left out (`band.created` says it). The journal knows no feature: each module gives a `JournalSource` for its target type (`modules/songs/journal.ts`, `modules/bands/journal.ts`), passed to `journalRoutes` in `src/app.ts`. A new feature with journal entries adds its source there. The web app gives each action a sentence (`src/components/band/band-journal.tsx`): a new band event needs one in both locales, or it isn't shown.
- **Kept one year** (`ACTIVITY_RETENTION_DAYS`): `purgeActivity` (`src/core/activity/purge.ts`) deletes older rows, run every night by the `purge-activity` cron job, which logs the count.
- Tests check the events with `activityOf(db, targetId)` (`src/test-deps.ts`) and delete the activity outside a band of their test users.

## Authentication

- Better Auth in `src/adapters/auth.ts`, mounted at `/api/auth/*`. Email + password, sessions in Postgres, password policy from `@coverband/shared` (`PASSWORD_MIN_LENGTH`). Admin plugin for the global role.
- Tables in `src/adapters/auth-schema.ts` were generated with `npx auth generate`, then adapted: when adding a Better Auth plugin, regenerate and compare.
- The default admin is created at startup from `ADMIN_EMAIL` / `ADMIN_PASSWORD` only if missing (`src/bootstrap.ts`).
- Users have `firstName`, `lastName`, `nickname`; Better Auth's `name` holds the display name (`displayName()`). Better Auth keeps them read-only (`input: false`): users change them with `PATCH /api/me` (`src/modules/profile/routes.ts`, `src/modules/profile/service.ts`), which recomputes `name`. Better Auth's `/update-user` is disabled (`disabledPaths`): it would let users set `name` freely and write `image`, which holds a storage key only the server may write.
- **Impersonation (#214, study 020):** admins view the app as a user (not another admin) with the admin plugin's `/admin/impersonate-user` and `/admin/stop-impersonating`: a real session of the user, with `impersonatedBy`, 1 hour. It is **read-only**: `impersonationReadOnly` (`src/core/http/impersonation.ts`, before Better Auth's handler) refuses every request but GET / HEAD / OPTIONS with 403 `impersonation_read_only`, Better Auth's included, except `stop-impersonating` and `sign-out`; it looks the session up for writes only. Starting records `user.impersonated` (actor: the admin, target: the user) from Better Auth's session `create.after` hook, outside its transaction; request logs carry `impersonatedBy`.
- Password reset (`/request-password-reset`, `/reset-password`): the email's link (1 h, single use) goes through Better Auth's `/api/auth/reset-password/:token`, which redirects to the web app's `/reset-password?token=` or `?error=INVALID_TOKEN`. The email is in the request's `Accept-Language` (the web app sends its language). The answer is the same whether the email has an account or not (only the response time differs, an accepted leak). A reset revokes every session; `/change-password` is called with `revokeOtherSessions`.

## Invitations and onboarding

- `src/modules/invitations/service.ts` is the only way to get an account. Band leader invitations (`/api/admin/invitations`) answer in react-admin's shape for the admin app (#250): a list `{ data, total }`, a created or revoked one `{ data: { id } }`. Role `leader` (creates a band, sent by an admin) or `musician` (joins a band, sent by that band's leader).
- Functions take an `InvitationScope` (`LEADER_INVITATIONS` or the musicians of one band), so an id from another scope is not found.
- Only the token's SHA-256 hash is stored. If the email can't be sent, the invitation is deleted.
- Accepting goes through the public `/api/invitations/:token` routes and `src/modules/onboarding/service.ts`: everything (account if new, band, membership, invitation consumed) in **one transaction, nothing before the last wizard step**. Onboarding owns no table: it calls each module's service with its transaction (`lockPendingInvitation` / `consumeInvitation`, `createAccount`, `createBand`, `addMember`), and each records its own event. A new account is created with Better Auth's password hasher and the `credential` account shape, then logged in. Someone who already has an account must be logged in as the invited email.

## Notifications

Notes from the app's team (#260, brief 025, `src/modules/notifications/`): `notifications` (kind `admin-modal` and sender `team`, from `NOTIFICATION_KINDS` / `NOTIFICATION_SENDERS` in `@coverband/shared`, both Postgres enums; the text as typed, up to `NOTIFICATION_TEXT_MAX_LENGTH`; who sent it, null once deleted) and `notification_reads` (one row per user and note, whichever device). An admin sends one to every user with `POST /api/admin/notifications` (`teamNoteBody`; `notification.sent`) and lists them with `GET` (react-admin's shape, newest first, with `recipients`: users whose account existed when it was sent, and `readers`). A user gets their unread notes with `GET /api/notifications` (sent after their account was created, oldest first) and reads one with `POST /api/notifications/:id/read` (204, again too; 404 for a note that isn't theirs; `notification.read` the first time). Push notifications (#261, study 022): `push_subscriptions` (one row per device, the endpoint unique: a browser logged in as someone else moves to them). `GET /api/push/key` gives the public VAPID key (null: push off), `PUT /api/push/subscription` saves a device (`pushSubscriptionBody`; 404 with push off; 400 for an endpoint that isn't a browser's push service over HTTPS, `isPushService`: the server will send there; `user.push_enabled`), `DELETE` removes one of the user's own (`user.push_disabled`). The keys (`src/adapters/push.ts`, `AppDeps.push`): `VAPID_PRIVATE_KEY`, a P-256 key in PEM (OpenTofu's `tls_private_key.vapid` in production, never replaced: every subscription was made with it; `.certs/vapid.pem`, made once by the dev scripts, `src/dev/vapid.ts`; a throwaway per end-to-end run), turned into the raw keys by `vapidKeys`, the subject being the app's URL when HTTPS, else `MAIL_FROM`'s address (`vapidSubject`: VAPID takes only `https:` and `mailto:`); `PUSH_SERVICE_HOSTS` (default: Chrome's, Firefox's, Apple's, Microsoft's; the end-to-end tests' fake is `localhost`). A subscription keeps the app's language on the device. **Sending** (#262): a team note sent by an admin is also pushed, during the request, to every device whose endpoint is an allowed push service (`pushTeamNote`: `PUSH_CONCURRENCY` at once, `{ title, body, url }` with the signature in the device's language, the note's start as body, `pushBody`, `/` as URL; a day of TTL) by a `PushSender` (`createWebPushSender`: `web-push`, which signs with the VAPID keys and encrypts for the device; `createMemoryPushSender()` in tests). One `push_deliveries` row per device (`sent`, `failed`, `gone`): a gone device (404, 410) is deleted, a failure logged as an `error` (the push service's host, never the endpoint). The answer gives `devices: { reached, failed }`, the admin's list `devicesReached` and `devicesFailed`. A later job or queue would call the same function (study 022, "Where sending runs").

## Bands

Name and slug logic in `src/modules/bands/service.ts`. **Suspended bands** (#248): an admin sets `bands.disabled_at`; `requireMember` then answers the band's members 403 `band_suspended` on every band route (non-members still get the 404), and the user's band list says `suspended`. Events `band.disabled`, `band.enabled`; `band.deleted` is recorded outside the band (`band_id` null), with no name. Band names are unique case-insensitively; the slug comes from `slugify` in `@coverband/shared`.

Instruments are per band membership (`member_instruments`, `src/modules/instruments/service.ts`): an ordered list (the first is the main one) of known codes or free text, never both (a database check). Values are always cleaned with `cleanInstruments` (`parseInstrument` from `@coverband/shared`: free text matching a known instrument becomes its code, unknown codes become free text, duplicates dropped, at most `MAX_INSTRUMENTS`). Members change only their own (`PUT /api/bands/:bandSlug/members/me/instruments`). Free text used in at least two bands is suggested to everyone (`GET /api/instruments/suggestions`); one band's own labels never are.

## Songs

A band's repertoire (`songs`, `src/modules/songs/service.ts`, routes in `src/modules/songs/routes.ts` under `/api/bands/:bandSlug/songs`): every member lists, adds and edits songs. Title and artist identify a song **without a unique constraint**: a song matching another one of the band (`findDuplicateSong` / `songKey` from `@coverband/shared`: case, accents, punctuation and spaces ignored) is refused with 409 `song_duplicate` unless the request sends `confirmDuplicate: true`, which the web app asks for ("add anyway"). An edit is only checked when its title or artist changes. Durations are seconds (`standardDuration`: the original, `ownDuration`: the band's), typed as `m:ss` (`parseDuration`). Details (#89), all optional: `key` and `bandKey` (codes from `MUSICAL_KEYS`: 12 major, 12 minor, spelled as usual, shown with `keyLabel` / `keyShort`), `tempo` (BPM, `SONG_TEMPO`), `style` and `notes` (free text, blank is null). Status and energy (#90): `status` (`SONG_STATUSES`: proposed → learning → ready, a Postgres enum, new songs are proposed) and `energy` (1 to `MAX_ENERGY` = 3 peppers, null: not rated), one band-wide value each. A new status records its own `song.status_changed` (data: the status code, which the journal returns); other changed fields go in `song.updated`. Archive and delete (#91): any member archives and restores (`POST …/archive`, `…/restore`, `archived_at`; `GET …/songs?archived=true` lists them; archived songs don't count as duplicates); a band leader deletes for good (`DELETE …/songs/:songId`). **Whatever uses a song (setlists) must reference it with a foreign key that refuses deletion (`on delete restrict`)**: `deleteSong` turns that refusal into 409 `song_in_use` ("archive it instead"). Events `song.archived`, `song.restored`, `song.deleted`; a deleted song's journal entries say "a song". Links (#92, `song_media`, `src/modules/songs/media.service.ts`): `POST /…/songs/:songId/media`, `PATCH` / `DELETE …/media/:mediaId`, returned with the song (`GET …/songs/:songId`, oldest first); http(s) URLs only (`parseMediaUrl`), an optional title, instruments cleaned with `cleanInstruments`, at most `MEDIA_LIMITS.perSong`. The provider isn't stored: `mediaProvider(url)` reads it from the domain, so new providers apply to older links. Each change records `song.updated` with `fields: "media"`. Lyrics (#129): `lyrics` (free text up to `SONG_MAX_LENGTH.lyrics`, blank is null) and `lyricsSource` (`LYRICS_SOURCES`: `lrclib` or `typed`, a Postgres enum), returned with one song only, never in the repertoire's list. The source follows the lyrics (`withLyricsSource`): none without lyrics, kept when they're edited, `typed` for new ones unless the request says `lrclib`; it never changes alone. A lyrics change records its own `song.lyrics_changed`. Lyrics search (#130): `GET …/songs/:songId/lyrics/search[?q=]` (by the song's title and artist, or free text with `q`, #138; members, `LYRICS_SEARCHES`: 30 per hour per user) asks a `LyricsProvider` (`src/adapters/lyrics.ts`, `AppDeps.lyrics`: LRCLIB at `LRCLIB_URL` with the app's `User-Agent`, nothing cached; `createMemoryLyricsProvider()` in tests) and returns `{ matches, instrumental }`: `rankLyrics` (`lyrics.service.ts`: each text once, closest to the song's original duration first, `LYRICS_MATCHES` = 5), and `onlyInstrumental` (#136: every entry with the song's title is marked instrumental); nothing is saved: the web app saves the chosen lyrics with `lyricsSource: "lrclib"`. The service down or refusing: 503 `lyrics_unavailable`. Activity: `song.added`, `song.updated` (with the names of the changed fields); the journal shows the song's current title. The whole repertoire for offline use (#165): `GET …/songs/details` (members), every current song as `GET …/songs/:songId` shows it (lyrics, who added it, links), in the repertoire's order (`songDetails`, `mediaOfBand`); the list breaks ties by id, so confirmed duplicates keep one order.

## Documents

A song's documents (#238, `song_documents`, `src/modules/songs/documents.service.ts`, routes in `documents-routes.ts` under `/api/bands/:bandSlug/songs/:songId/documents`, members): a title, instruments (`cleanInstruments`), who added it (`addedById`, the name shown), the date; listed with the song (`GET …/songs/:songId`, oldest first) and in `…/songs/details` (offline), each with its file's `url` (`documentUrl`). Kinds (`DOCUMENT_KINDS`): photo, PDF, Guitar Pro, MuseScore, read from the file's first bytes and its name's extension together (`documentType`, `document-types.ts`, tested), never the declared type; never SVG. Photos (the browser shrinks them) and PDFs keep their type and are shown (`inline`); Guitar Pro and MuseScore files are `application/octet-stream` downloads (`attachment`); the name is the title (`fileName`, ASCII and UTF-8 forms); never replaced, so cached for good. `POST` a multipart form (`addDocumentBody`: `file`, `title`, `instruments` as JSON), its own body limit (`DOCUMENT_UPLOAD_MAX_SIZE` in `src/app.ts`); limits (`DOCUMENT_LIMITS`): 4 MB (413 `document_too_large`), 20 per song (409 `too_many_documents`), 500 MB per band (409 `band_storage_full`), other files 400 `document_invalid`. The file is stored first (`bands/{id}/documents/{uuid}.{ext}`) and deleted again when the document isn't saved. Any member edits the title and instruments (`PATCH`, `song.updated` with `fields: "documents"`); the member who added it or the band leader deletes it (403 for the others; `song.document_removed`), its file then; `song.document_added` (data: the kind). A deleted song deletes its documents (cascade) and then their files (`deleteSong`).

## Autofill

"Search and add" for a new song (#199, brief 020): `GET /api/bands/:bandSlug/autofill?title=&artist=` (`src/modules/autofill/`, members) looks the song up online, nothing saved: the member chooses in the web app. Deezer's public API (no key) through a `MusicCatalog` (`src/adapters/deezer.ts`, `AppDeps.catalog`, `DEEZER_URL`; `createMemoryCatalog()` in tests) gives `track`: the best match (same title and artist, then same artist, else Deezer's first; a plain "artist title" search, its advanced syntax finds nothing), its link and album id (`findTrack`), then the album's first genre (`albumGenre`); both throw when Deezer fails. YouTube (#200) through a `VideoSearch` (`src/adapters/youtube.ts`, `AppDeps.videos`, only when `YOUTUBE_API_KEY` is set; `YOUTUBE_API_URL`, `YOUTUBE_THUMBNAILS_URL` for the fakes; `createMemoryVideoSearch()` in tests): the Data API's `search.list` (music category, 15 videos), then `videos.list` (durations, full descriptions); `rankVideos` keeps the best `VIDEO_PROPOSALS` (5): "Artist - Topic" channels and "Provided to YouTube by…" (album tracks, audio only) first, then the artist's channels; live, cover, karaoke, lyrics, remix, acoustic... versions last unless the song's title asks for one, and then the others last (`videoScore`). The answer's `videos` are null without a key or when YouTube fails (a quota exceeded, a bad key), so Deezer's details still come. A service that fails (#208) is logged as an `error` by the service and listed in the answer's `failed` (`deezer`, `youtube`; Deezer's album failing keeps the track, without its genre): the web app says which one had an error, never "nothing found". Thumbnails go through the API (`GET …/autofill/thumbnails/:videoId`, members, checked id, cached a day; none: 404; YouTube failing: logged, 502): no security policy change, phones never contact Google. Quota: `AUTOFILL_SEARCHES`, 15 per band and day (`rateLimitBy`, keyed by the band: YouTube's free quota is shared by the app), 429 over it. Link search (#220): `GET …/autofill/tracks?q=` (members) gives Deezer's tracks for free text (`searchTracks`: up to `TRACK_MATCHES` = 5, in Deezer's order, without their genre); nothing saved; `TRACK_SEARCHES`, 30 per hour per member; Deezer failing is a 503 `deezer_unavailable` (`CatalogUnavailableError`, logged with its cause).

## Files

- Object storage through a `Storage` (`src/adapters/storage.ts`, `AppDeps.storage`): `put`, `get` (a stream, or null), `delete`. Bun's built-in S3 client, no SDK. Garage locally (`docker/garage/`, started and prepared by `bun run db:up`, also in CI), Scaleway Object Storage in production: only `S3_*` configuration. In production, the bucket and its key are created by `infra/` (OpenTofu).
- The bucket is private: files are served by API routes that check who may see them, never by public bucket URLs.
- Keys are paths with a fresh UUID per version (`users/{id}/avatar/{uuid}.webp`): a new file gets a new key, and the old object is deleted.
- Tests use `createMemoryStorage()`; the S3 integration test runs when `S3_ENDPOINT` is set (locally and in CI).
- **Avatars** (`src/modules/profile/avatars.ts`): `PUT` / `DELETE /api/me/avatar` (raw body, the browser has already cropped and resized it; WebP or JPEG, checked by the first bytes, never the declared type) and `GET /api/users/:id/avatar` (the user, admins and band mates, 404 for anyone else). `users.image` holds the storage key; `avatarUrl()` from `@coverband/shared` turns it into the versioned URL, cached for good.
- Image formats are recognised by their first bytes with `imageType(bytes, accepted)` (`src/core/images.ts`: WebP, JPEG, PNG; never SVG, which can carry scripts); `InvalidImageError` (400 `invalid_image`) and `ImageTooLargeError` (413 `image_too_large`).
- **Band logos** (#175, `src/modules/bands/logo.ts`): the band leader uploads with `PUT /api/bands/:bandSlug/logo`, a multipart form (`logoUploadBody`: `logo`, `thumbnail`) prepared by the browser: the logo fitted within `LOGO_SIZE` (never cropped, for print) and its `LOGO_THUMBNAIL_SIZE` thumbnail, PNG, WebP or JPEG, under `LOGO_MAX_BYTES` / `LOGO_THUMBNAIL_MAX_BYTES`. `DELETE …/logo` removes it. No background any more (#189): `bands.logo_background` and its enum were taken out of the schema in 0.6.0, then dropped by the next release's migration (#191). Members get the files from `GET …/logo` and `…/logo/thumbnail`. `bands.logo_key` and `logo_thumbnail_key` (`bands/{id}/logo/{uuid}[-thumbnail].{ext}`, read through `ownLogoKey`); the band (its page, the list, the genre update) carries `logo: { url, thumbnailUrl } | null` (`bandLogo()` from `@coverband/shared`, versioned URLs). Every change records `band.logo_changed` (data: `change`: added, replaced or removed; older events may say background); the journal says changed or removed.

## Emails

- Sent over SMTP by a `Mailer` (`src/adapters/mail/mailer.ts`): Mailpit locally, Scaleway TEM in production, so the provider is only `SMTP_*` configuration.
- One function per email in `src/adapters/mail/templates.ts` returning an `EmailContent` per language (`Record<Language, ...>`, so a missing translation fails the typecheck), rendered by `renderEmail` (`src/adapters/mail/layout.ts`: inline-styled HTML + plain text, every value escaped).
- Send an email in the recipient's language. The one exception: the contact form's email to the app's team, in English (`contactEmail`).
- **Contact form** (#234, `src/modules/contact/`): `GET /api/contact` (logged in) says whether it's offered (`CONTACT_FORM_RECIPIENT` set, `AppDeps.contactRecipient`); `POST` (`contactBody`: a `CONTACT_SUBJECTS` code, a message of `CONTACT_MESSAGE` length; a bug report's page and the language) emails the recipient with the user's address as Reply-To (`Mail.replyTo`), the subject line from the code (nothing typed in a header), a bug report with its context (the server's version and build, the request's User-Agent, the page, the language). `CONTACT_EMAILS`: 5 a day per user. `contact.sent` (data: the subject's code) once sent; a failed send is a 500 and records nothing.
- Tests use `createMemoryMailer()`; the Mailpit integration test runs when `MAILPIT_URL` is set (locally and in CI).
