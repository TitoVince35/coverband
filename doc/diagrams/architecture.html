Coverband architecture

Where the code lives, how a merge reaches production, and what the one production container talks to. Checked against infra/ (OpenTofu) and the deploy workflow.

What each piece does

Development

  • Vince's laptop: product design and briefs (doc/briefs/), prompting, reviewing and merging pull requests. Runs the whole stack locally with Docker (Postgres, Mailpit, Garage).
  • Claude Code: full-stack developer and UX/UI consultant: studies, code, tests, issues and pull requests.

GitHub

  • Git repository: dev for features, main for production, changed only by a release pull request.
  • Actions: CI on every pull request (audit, lint, typecheck, tests, build, end-to-end, production image); the deploy workflow on every push to main.
  • Projects: the Kanban board (Backlog, Todo, In progress, In review, Done), Epics with their sub-issues.

Scaleway, in Paris

  • Serverless Container: one image, where the API (Hono on Bun) also serves the PWA and, on its own hostname, the admin app. Stateless: it keeps nothing in memory or on disk.
  • Serverless SQL Database: PostgreSQL, through Scaleway's connection pooler.
  • Object Storage: documents, band logos, avatars and setlist exports, served only through the API.
  • Transactional Email: invitations and password resets, over SMTP.
  • Domains & DNS: coverband.fr, its app and admin hostnames, and the email records.
  • Cockpit: the container's logs. Cron trigger: the nightly activity purge. Container Registry: the images Actions builds.
  • All of it is code in infra/ (OpenTofu), with a monthly budget alert.

On the Internet

  • Band members' phones: the installed app, which keeps setlists, lyrics and photos for offline use.
  • Browsers' push services: no provider account. The server signs each notification with our own VAPID key and sends it to the push service of the phone's browser, which delivers it.
  • Music & lyrics APIs: LRCLIB for lyrics, Deezer and YouTube for "Search and add".

From a brief to production

  1. Vince writes a brief; once it's settled, Claude plans it as an Epic and issues on the Projects board.
  2. Claude develops each issue on its own branch and opens a pull request to dev; CI runs every check, end-to-end tests included.
  3. Once green, the pull requests are merged into dev.
  4. A release bumps the version on dev and opens a pull request from dev to main; its CI must pass again.
  5. The merge to main deploys: Actions builds the image into the Container Registry, migrates the database, rolls out the container, checks that the new build answers, and tags the version.
