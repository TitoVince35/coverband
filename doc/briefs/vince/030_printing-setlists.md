> 🕒 Brief settled on Thursday 2026/11/12 13:51

- Main output format: pdf (Print button)
- Alternative raw format: docx (Export to docx button)

## Generation cycle

Band members may want to generate a setlist export (pdf or docx). One export should be linked to a setlist version and cached in the band's bucket.

Thus, only a modified setlist will generate a new document when asked for an print/export.

## Creating the docx

The docx export does not focus on layout and page breaks. It is more like a raw export.
No font consideration.

### Document structure

```xml
<MainHeader/>
<Part1>
    <PartHeader />
    <Song1/>
    <Song2/>
    ...
    <SongN/>
</Part1>
...
<PartN/>
```

#### MainHeader
The header is a table with 2 columns:
- Band logo (1/3 width max when rectangular)
- Setlist info on 2 lines:
    - Setlist title | Creation date
    - Band name | Total number of songs | Total duration

#### PartHeader
The part header contains:
- Part title
- Part duration

#### Song
Information on one line: Index (in setlist part) - Title (bold) - Artist - energy - tempo - key - duration 

#### Footer
Footer on each page: "Generated by Coverband app on `creationDate`"

## Creating the pdf

A setlist pdf can have one or many pages. Most of the time we are aiming to one page.

Bottom line: one part of a setlist cannot be spread over multiple pages.

A long set can be split in two columns when this can avoid a linebreak.

A setlist is printed on A4 paper and must be as readable as possible (large, bold characters, no serif). The most important element is the song title, the rest can be smaller.


### Document structure

This is an example of a large playlist.
It has a big first set that we can display on 2 columns on the first page.
On the second page, 2 more sets can share the same page without columns or linebreak.

```xml
<MainHeader/>
<Part1>
    <PartHeader />
        <ColumnLeft>
            <Song1/>
            <Song2/>
            ...
        </ColumnLeft>
        <ColumnRight>
            <Song11/>
            <Song12/>
            ...
            <SongN/>
        </ColumnRight>
</Part1>
<PageBreak/>
</Part2>
    <PartHeader />
    <Song1/>
    <Song2/>
    ...
    <SongN/>
</Part2>
<Part3/>
```

The MainHeader and PartHeader pseudo-components share the same information as for the docx.
The Song shows less than in the docx: Index - Title (bold) - Artist - tempo - key. No duration nor energy for a song.
Also there is the same Footer on each page of the pdf.

## Claude's recommendations (settled)

### How it works

- **Made by the API, cached in the band's bucket.** The file is made when someone asks for it: nothing runs in the background. Libraries: `pdfkit` for the PDF (plain JavaScript, runs on Bun, measures text for the layout), `docx` for the docx. No headless Chrome (too heavy for the container), no generation in the browser (the cache would be pointless).
- **Buttons:** Print opens the PDF (the phone or browser prints it from there); "Export to docx" downloads the file. Offline, both stay visible but disabled, along with the offline banner.
- **Who:** every band member, archived setlists included.

### Decisions

1. **When a new file is made:** the cache key is a fingerprint of everything the document shows (each song's title, artist, energy, tempo, key and duration, the parts, the band's name and logo, the format, the language), not the setlist's version alone, so a renamed or re-timed song gives a new file. A table keeps the latest file per setlist, format and language; the previous file is removed from the bucket when it is replaced.
2. **Language:** the language of the person who asks; one cached file per language.
3. **Dates:** the header's date (the MainHeader's "Creation date") is the setlist's last change; the footer's ("Generated by Coverband app on …") is the day the file was made, without the time.
4. **Tempo, key and duration:** the tempo as "120 BPM", just before the key (added after review); the band's key when the band transposes, otherwise the original; the band's own duration when set, otherwise the original, as in the app. Totals (a part's, the setlist's) add "(2 songs without a duration)" when some are missing.
5. **Energy:** the number in the docx ("Energy 3"); none in the PDF (changed after review, below).
6. **Logo:** converted to PNG on the server when the export is made (`sharp`), since neither format holds WebP.
7. **PDF layout, when a part doesn't fit:**
   - Song line: the title bold and large; artist, tempo and key smaller (no energy nor duration, changed after review). In two columns, the artist, tempo and key go on a second, small line.
   - A part takes one column if it fits on the page, otherwise two columns, otherwise starts a new page. Several parts share a page when they fit. Last resort, the font gets smaller: a part is never split across pages (50 songs at most, so 25 lines per column, about 20 pt on A4).
   - One bundled sans-serif font (Inter or Noto Sans, free to embed): the PDF's built-in Helvetica can't print every character in song titles.

### Changed after review (Thursday 2026/11/12)

- The PDF shows no song's duration nor energy: each song's index, title, artist, tempo and key. The parts' and the setlist's durations stay.
- Every song shows its tempo ("120 BPM") just before its key, in both formats; in the PDF, tempos and keys each have their own column, so they line up.
- The main header, in both formats: the setlist's title, then the date; the band's name, then the number of songs and the total duration ("The Covers … 40 songs · 2 h 39 min").
- Keys print with `#` and `b` in the PDF ("F#m", "Db"): the bundled font has no ♯ nor ♭ (found by #299's examples).

### Also

- **Cleanup:** a setlist's files are removed from the bucket along with the setlist, and along with the band.
- **Limit per user:** 30 files made per hour, counted only when a file is actually made (a cached file is free). Editing and printing again a few times before a gig stays far below it; a script asking in a loop is stopped.
